# 留痕：空格隔开处出现下划线（程序侧误转）·根因与收严（2026-10-17）

> 属主真机："最后看到的内容，本身是空格隔开的地方，有下划线（横线），这个是程序侧的问题吗？"
> 结论：**是程序侧**。根因在 `contentCleaner.wrapBareBlankRuns` 的"裸空格串 → 填空横线"启发式（规则③），已收严。

## 一、链路（为什么空格会变成下划线）

```
模型输出裸空格串（　　/&emsp;）
  → contentCleaner.wrapBareBlankRuns 规则③「中句语义填空位」
  → 包成 <u class="blank-N">&emsp;</u>
  → 渲染（CSS border-bottom）/ docx（NBSP + 下划线）
  → 卷面上出现一条本不该有的横线
```

规则③的本意：模型该给空位却只写了空格（如"求 4 个　　　　相加"），程序兜底补载体。
但它是**启发式**：判据只有"位于两个汉字之间 + 该段空格足够宽"，没有"这里确实是空位"的证据。

## 二、根因（两个盲点，命中其一即误画横线）

| 盲点 | 说明 |
|---|---|
| **罗列守卫只认同宽** | 原判据"同句内还有一处**宽度 ±2** 的裸空格 → 判为词表/列分隔、不转"。而实际列分隔宽度常不一致（如 `温暖　　寒冷　　　　　明亮`：2em 与 5em）⇒ 守卫失效，**两处都被画成横线** |
| 无第二道证据 | 除"相邻已有载体"外，没有其它证据能说明该空格是不是排版分隔 |

**为什么别的空格不会画线、偏偏这几处会**：只有"两侧最近可见字符都是汉字、且同句里没有同样宽的空格"这一个夹缝被选中；一旦宽度不一致就成了"孤立空位"。

## 三、处置（收严，不删功能）

`hasSiblingGap` 判据由"同宽 ±2"改为 **"同一分句内只要还有第二处裸空格段 → 整段按排版分隔，一概不转"**。

| 情形 | 改前 | 改后 |
|---|---|---|
| `温暖　　寒冷　　　　　明亮`（宽度不同） | 两处转横线（误） | 保留原空格 |
| `温暖　　寒冷　　明亮`（同宽） | 保留 | 保留 |
| `求 4 个　　　　相加的和`（同句唯一空位） | 转横线 | 转（不变） |
| `有　　位，从右起数出　　位`（分句各一处） | 各转 | 各转（不变） |
| `0.6×0.3＝　×　＝　。`（算式空位链） | 转 | 转（走"运算符邻接"分支，不受本次收严影响） |

**取舍**：宁可"该画没画"（空格保持空格，模型侧本就要求用显式载体），也不要"不该画却画"（凭空长横线）。
这也与"程序不猜语义、不改正文"的一贯口径一致。

## 四、还有一处同类（未动，观察）

规则②「行尾 / 句读前」同样会把空格包成横线——它只影响**行末**，不会在词与词之间长线。
若下一份产物出现"行末多出一条横线"，那就是它，处置方式相同（收严或停用），届时按同一口径办。

## 五、验证

- `bareBlankWrap`（含新增"宽度不同的列分隔"用例）＋`normalizeBlankMarkers` 全绿。
- 全量：见提交信息；构建通过。
- **须真机复核**：词表/并列项之间的空格是否不再出现横线；该有横线的填空是否仍在。
