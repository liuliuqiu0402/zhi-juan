## 一、需求基线（用户原话要点）

1. 项目主要用途：**大量制作学习资料**（批量生产场景）。
2. 学习资料以**具体内容为王**（内容是核心交付物）。
3. 内容须符合**新课标**要求，能**直接作为正式考卷**使用、能**直接用于教学**。
4. 必须**从根本上规划解决**，不能依靠打补丁（"你应该且必须做到"）。
5. 生成时注入大量长指令——**寻找其他方案实现最终目的（资料生成）**。
6. 系统定位是**生产工具**：要能**流水线化**，所有问题**从源头彻底解决**。

## 三、核心决策（讨论结论）

### 决策1：单一事实源（SSOT）——规范源在指令库，执行器从指令库派生

双路径不一致时，**修复方向不是"把注入指令改成硬编码板块指令"**，而是反向：

- **指令库 = 规范源**（业务规范、内容要求的唯一定义处，用户可在 UI 维护）。
- **分步板块指令 = 指令库的派生视图**（运行时组装，而非代码内硬编码）。
- 分步模板中的硬编码（角色称谓、分值政策、标题格式、题量条款）应改为**从指令库按 genType/学科/学段查询组装**。
- 判定原则：**内容语义以指令库为准；执行机制以分步引擎为准**。

理由：
1. 指令库是用户可维护的规范层（`addCustomInstruction/updateCustomInstruction`），分步模板是代码，用户改不了。
2. 若用户自定义学科角色/分值/格式，分步路径必须感知——只有从指令库组装才能做到。
3. 单一事实源避免两处维护、两处漂移。

### 决策2：指令分层（替代"巨量长指令注入"的方案）

| 层 | 内容 | 落点 | 机制 |
|---|---|---|---|
| 规范层（稳定） | 角色/红线/格式/顶层/尾约束/素养 | System prompt | 固化，模型"永久记忆"（已实现 `splitSystemAndUser`） |
| 任务层（每份资料） | 核心任务/板块结构/题量分值 | User prompt | 按资料动态组装 |
| 板块层（分步） | 单板块约束+教材素材+格式 | 板块短指令 | 分步引擎逐板块调用 |
| 内容层 | 教材原文/例题/情境 | 检索注入 | `retrieveBlueprintSegments`/`semanticRetriever` |

### 决策3：代码确定性优先（源头根治，非事后打补丁）

能用代码保证的，不让 AI 决定：
- 卷首/密封线/时长/满分：`assemblePaperHeader` 代码拼装（已做）。
- 板块规划/分值校验：`validateSectionPlans`/`parseQuestionCount`（已做）。
- 格式标签/填空规范：代码侧模板+硬规则校验（已部分做）。
- 方向：把"事后修复"前移为"事前约束"，质检规则继续向代码侧收敛。

### 决策4：内容为王 → 教材知识库 + 检索增强

- 生成不靠模型凭空写，靠**教材内容检索注入**（原文/例题/情境/命题素材）。
- 深化方向：教材语料积累、检索精度、知识图谱质量——这是"具体内容为王"的根基。

### 决策5：流水线化（生产工具定位）

- 每类资料 = 明确"配方"（Recipe）：genType × 板块模板 × 质检规则 × 输出规范。
- 批量任务队列：一次勾选 N 单元/课时 → 批量生成。
- 生成结果进入资料库（HistoryModule），可追溯、可复跑。
