# 实发语义逐条复核 · 覆盖台账（2026-10-01 起）

> 用途：落实用户裁定"**工具库内、工具库外的所有实发给模型的都这样处理，不能漏，不能偷懒**"。
> 判定标准＝ `docs/design/指令改动标准-可机检清单.md` §六「**八问固定顺序**」（①三维度 → ②课标原文/原义 → ③啰嗦 → ④精准 → ⑤诱导 → ⑥拼接整体 → ⑦质量 → ⑧位置与结构；**不得颠倒、不得跳问**）。
> 状态口径：`未开始` → `逐条中`（正在按序过，附已过条数）→ `已过`（该文件全部实发文本逐条过完，附改动与字数）。
> 纪律：每批改动后跑全量测试；动到测试锚点写明依据（**以产出为准**——允许删／改准，不再"只准收紧"）。

### 双向交叉校验（2026-10-01 实测 · 探针已删）

> 用户提醒："**你能确保实发它是采集完整了吗？得两个方面交叉看，才能确保不漏吧？**"

**机制（双向，差集必须为空或有明确归类）**：
- **A 面 · 源 → 实发**（防**漏采集**）：716 条逐个查"它的文本是否出现在实发里"；缺失者必须逐条定性，不得笼统当作"没用到"。
- **B 面 · 实发 → 源**（防**漏登记源**）：实发里每一句回溯"它出自哪个源"；回溯不到的＝无源文本（动态拼接/调用层硬编码），**这类最容易漏**。
- **C 面 · 注入点反查**（元校验）：从代码里所有进 messages 的调用位反查，验证 A/B 两面本身的前提没漏。

**首轮实测结果（675 份实发 vs 716 条源）**：

| 方向 | 差集 | 说明 |
|---|---|---|
| A 源→实发 | **501 条未以原文出现在实发** | ⚠️ **不能一概算漏采集**，实测至少三类：①**程序消费**（如卷首标题、考试时长——由程序件序/拼装处理，本就不进模型）；②**改写后注入**（蓝图条款被重写成注入句，措辞变了、语义在）；③真的不进模型。**必须逐条定性**——这正是"哪些是给模型的"的答案载体 |
| B 实发→源 | **194 处无源句** | 🔴 **暴露源名册缺口**：如「【锚点清单】」「说明：下面列出的是本次涉及的内容与材料…」「知识主题（第1层）…」等，是 `injectionManifest.buildUserMessagePrompt` 的**框架文案——硬编码在调用层、不属于任何"库"**。这类"库外硬编码"必须补进名册（另注：探针自造的 `一、主题／· 知识点` 属测试输入，非真源，已排除） |

**方法论要点（由此确立）**：**蓝图库不是逐字注入，而是"改写后注入"** → 因此"源↔实发"的对齐须按**语义**；仅"逐字相同的共享块"（如题目自洽、质量底线、尾约束）才可按**逐字**复用判定。

**下一步**：补全"源名册"（先把 `buildUserMessagePrompt` 等库外框架文案登记进来）→ 重跑 A/B 两面 → 直到**两侧差集全部有归类或归零**；501 条逐条定性（程序消费／改写注入／不进模型）。

### 注入口径（2026-10-01 用户对账后定 · 三条）

> 用户原话："**源进实发，不要改写；源和实发都能对上账，这样就不会出现上面的无源句了吧？**"

| # | 口径 | 适用与边界 |
|---|---|---|
| 1 | **陈述性条款：逐字注入、不得改写** | 指令库 cell、质量底线、题目自洽、尾约束、答案格式等**给模型的判据/要求**——它们本来就是逐字注入，**必须继续保持逐字**，账才对得上 |
| 2 | **结构化参数：不进实发；必要时派生一句并登记** | 分值/时长/题数/卷首标题/页码等是**参数不是句子**，由程序消费；若确需模型知道，则派生成一句（如"本卷满分 100 分"），**该派生句也须登记为源** |
| 3 | **每句必须"有主"——无源句的根治不是"禁止改写"，而是"消灭无主句"** | 实发里每一句都必须能指向一个源条目：**原始源**（库条目）或**登记在案的派生源**（如 `injectionManifest` 的框架文案、`programAttach` 各段、调用层 inline 文案）。**194 处无源句正是"无主句"**——要么登记为派生源，要么删/合 |

→ 结论：**"不改写"×"每句有主"两条一起用，A/B 两面差集才会真正归零。**

### 两侧差集的消除口径（2026-10-01 · 讨论稿）

> 用户提问："194 条，你有标准可以消除的，**501 条呢**？我们先讨论，讨论定了之后，再看**先把两侧差集跑为零，还是先改动后跑**。"

#### 一、194 条（实发→源：无主句）——已有标准，二选一

| 处置 | 适用 | 判据 |
|---|---|---|
| **登记为派生源**（变成"有主"） | 有意设计的框架文案，如 `injectionManifest.buildUserMessagePrompt` 的【锚点清单】【素材使用约定】等 | **它对模型有实质约束或信息** → 登记"调用层派生源（由哪个函数产出）" |
| **删 / 合** | 包装性、说了等于没说的过渡句 | 过八问③（能否更短）⑥（是否重复）→ 删或合并 |

#### 二、501 条（源→实发：未以原文进实发）——新增口径，**四类定性**

> 注：501 是**字符串级**计数（`stringsOf` 抽出的字段值），主要来自蓝图库（120＋54 结构）与规则库 promptHint，**不等于"716 条里有 501 条没进模型"**。

**逐条问三问，落入四类之一（每类都要有处置，不许留"未定"）**：

| 类 | 判据（三问） | 处置 |
|---|---|---|
| **T1 程序消费** | 程序代码里**有消费点**（读它来拼装/计算/校验，如卷首标题、考试时长、题数、页码） | **登记为"程序消费·不进实发"**，不算漏 |
| **T2 改写注入** | 实发里**有句子的语义与它对应**，但措辞被改写（如蓝图板块要求→注入句） | **建立"派生映射"**：登记「原始字段 → 派生注入句」，账即对上 |
| **T3 仅 UI/统计** | 只给编辑界面展示或统计用，与模型无关 | **登记为"仅 UI/统计"**，明确不进实发 |
| **T4 该进却没进** | 三问全不满足：程序不消费、实发无对应、也不是 UI 用 | 🔴 **真漏洞 → 报修补进**（这才是 501 里真正要动手的部分） |

#### 三、顺序建议：**先归零 → 再按份改动 → 滚动对账**

| 方案 | 评价 |
|---|---|
| 先改动、后跑对账 | ❌ 不建议：账没对上就动手＝**在不知全貌时改**（此前我已因此误判"按答案长度定宽""作答区行数上限"为程序职责而判错）；且改了文本→源句签名变化→差集**暴涨**，反而要重新对账 |
| **先归零、再改动**（建议） | ✅ 定性本身**就直接产出改动清单**（T4 补进、194 冗余删/合），所以"归零"不是纯准备；定性完按 **份**推进，**每改一份就重跑该份对账**（滚动，不必全量重跑） |

**待用户确认**：① 501 的"四类定性"口径是否采纳；② 顺序是否按"先归零 → 再按份改动 → 滚动对账"。

### 🔴 归零口径（2026-10-01 · 用户质询后先冻结，**先定后测**）

> 用户质询："**归零是要真正归零吧？以什么口径呢？不能这个凑一下，那个凑一下，没归零，再找一个凑一下吧？**"

**口径五条（测量前冻结，测量中不得改）**：

> 🔴 **此前错误（用户指出："实发＝库内＋库外吧？而且口径首先是库内和库外吧？然后才是库内、库外的具体位置吧？"）**：我原先是**扁平登记**——把库内、库外混在一张单子里按**函数名**去找，结果两头都错：**库外的真源**（框架文案、答案页 inline）被误判成"无主句"；**库内的分支**（`ANSWER_ROLES.other()` 四条分支）反被漏登记。**必须先分库内/库外（第一级），再分具体位置（第二级）。**

**恒等式（总账校验）**：**实发 ＝ 库内 ＋ 库外**（不重不漏）

| 级 | 划分 | 定位方式 | 记账 |
|---|---|---|---|
| **第一级** | **库内** ｜ **库外** | **库内**＝工具库六库里**可在 UI 编辑的条目**（有 id/key，用户可增删改）；**库外**＝**代码写死的、模型可见的文本**（只能改代码） | **两本账分开算**，各自出差集；不得混算 |
| **第二级** | 库内：**六库 × 条目（按分支）**；库外：**产出点**（函数 / 行 / 触发条件） | 库外产出点实例：`injectionManifest.buildUserMessagePrompt` 的框架文案、`useAiGenerator` 的答案页 inline 与调用层文案、`programAttach` 的段标题与拼接格式 | 每条登记 **provenance** |
| **转引规则** | `programAttach` 第③段（底线兜底）、渲染契约 = **转引库内**，**不算库外新源** | 记为"**库内某条目的第 N 处出现**"，防止重复计账 | — |

**库内/库外两侧的差集含义**：**库内差集**＝"库条目有没有进实发 / 进了几处"（查漏采、查改写）；**库外差集**＝"代码写死的句子有没有主"（查无主句、查该不该删）。

### 性质澄清：「程序附加段」（`buildProgramAttach`）是不是给模型的？

> 用户追问："我们发了指令，还有程序附加段，这个程序附加段中的，是需要模型理解遵守的吗？"

**答案：是。它是给模型的 system 指令，属于实发文本，必须纳入逐句复核。** 代码事实（`src/utils/programAttach.js` 文件头 ＋ `buildProgramAttachParts`）：

- **注入形态**：由生成端以 **system 角色（首条 system 消息）**注入，**不进委托正文**、不占委托书可编辑区；
- **内容三段**：① `buildRenderContract`——**渲染契约**（标记/形态协议）；② `buildValidatorPrompt` ＋ `getActiveFixPromptRules` 的 **promptHint**——生成前质检规则的提示；③ `floorClauseSections`——【输出格式】/【质量底线】**段级兜底**（委托正文已有该段则跳过），且与模板文本**逐字同源**；
- **设计定位**（准绳原话）："渲染契约语法、载体换算等**程序性知识不属于委托正文（解释权在程序侧）**"、"委托书只应有'这个活儿是什么、做成什么样算好'"。

**由此产生的处置判据（可减字）**：程序附加段里"要模型遵守"的条目，**逐条按附12 判**——
- **程序只校验、不代改**的（模型必须一次做对）→ **保留**（必须让模型知道）；
- **程序会确定性修正**的（如载体形态收口 `alignCarrierFormByDeclaration`）→ **可移出**（模型不必知道）；
- 且凡保留者**必须与指令库单源**，不得 system 与 user 两处各写一遍（此前实测 R-3 即此类重复）。
